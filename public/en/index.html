SAP Lakehouse on Databricks: production cost and procurement

At CBMM, I processed SAP data on Databricks, from the raw layer up to the views that feed the Power BI reports on production cost, procurement and sales. Final publishing in Power BI was done by the senior engineer; I delivered the views and maintained the jobs.

Source
SAP (Material Ledger and MM), the budgeting system through a federated SQL Server catalog, and market price series (Platts, CRU). I also mapped the origin of custom PP and SD transactions.
Architecture
raw exact copy of the source → harmonized hygiene, typing and metadata → serving dimensions and facts → views for Power BI · Unity Catalog and Delta Lake on ADLS Gen2
Orchestration
Adjusted and maintained the Material Ledger inputs job in Databricks Jobs: four harmonized loads in parallel, a sync step that only proceeds when all of them succeed, the actuals and inventory fact in the serving layer, and the Power BI refresh at the end.
Quality
Implemented the client's hygiene standard as reusable PySpark functions applied by column type: standardized text, distinct codes for missing values (undetermined, not applicable, does not exist, not informed), load metadata, MD5 hash key and soft delete.
Decision
No transformation in the raw layer. Hygiene starts in the harmonized layer, so any rule can be fixed and reprocessed without going back to SAP.
Modeling
Material and scenario dimensions in the serving layer, with an MD5 key and a comment on every column.
Lineage
Batch validation, through information_schema, of every object used by the reports (complete, partial, missing, divergent path) and tracing of the origin of the purchase requisition views.
Management
Sprints in Azure DevOps Boards: user stories with DoR and DoD, each task with the activities performed and hours spent, and a weekly hours close for the report sent to the client's data management.
Would do differently
Cast numeric values already in the harmonized layer: I found a market price stored as text, which made MIN compare alphabetically. And handle nulls before hashing, because concat_ws skips nulls and can produce the same key for different rows.
Stack
Azure Databricks · Unity Catalog · PySpark · Spark SQL · Delta Lake · ADLS Gen2 · Databricks Jobs · Lakehouse Federation · SAP · Power BI · Azure DevOps (Boards)
Status
Professional client project. No public code.

Azure tenant migration: Synapse, Storage, Key Vault and CI/CD

The client needed to cut costs and decided to move the data environment to a new tenant. I led the migration end to end, from Dev to Prod, checking parity with the old environment at every step.

Context
I was already supporting the environment and looking for cost savings for the client when the migration was decided.
Mapping
Full inventory of the old tenant: Synapse, Dev and Prod pipelines, triggers, tables, files in Storage, Key Vault secrets and each user's access, table by table and by permission type.
Strategy
Dev migrated gradually and validated → Prod table by table → pipelines through the reconfigured CI/CD, plus a dedicated pipeline to move the tables
Decision
In Prod, manual migration table by table: slower, but with full control over data loss and exposure of sensitive data.
Validation
Parity queries at every step: file types, row counts and size matching the old environment.
Adjustments
Key Vault secrets recreated (they do not migrate across tenants), triggers reconfigured, access replicated and the CI/CD pipeline working the same as in the old environment.
Management
Wrote the documentation for both tenants. Activities and hours logged daily in Azure Boards for the client's data manager; Azure DevOps administration (branch approvals, role-based RBAC).
